# Allocator overview

This allocator obtains memory from the operating system in **arenas**, divides
them into blocks, and reuses free blocks for later allocations.

## Build and test on Linux

```sh
make          # Build both shared libraries and the test/benchmark executables.
make check    # Run glibc and all three instrumented allocator strategies.
make clean    # Remove generated files in build/.
```

The outputs are `build/liballocator.so`, `build/liballocator_with_stats.so`,
`build/test_allocator`, and `build/benchmark`. The test executable uses glibc
unless a custom library is preloaded. For example:

```sh
LD_PRELOAD="$PWD/build/liballocator_with_stats.so" ALLOC_STRATEGY=best \
    ./build/test_allocator --require-custom
```

Both libraries can be used with `LD_PRELOAD`; the instrumented version provides
the diagnostics required by the custom-only tests. The compiler flags include
`-fno-builtin` to prevent allocation calls from being optimized away or rewritten
into recursive calls inside the allocator.

On macOS, build and run the Linux binaries through Docker:

```sh
docker build -t spp-allocator .
docker run --rm --network none -v "$PWD:/work" spp-allocator make
docker run --rm --network none -v "$PWD:/work" spp-allocator make check
```

## Benchmark

`benchmark.c` runs one deterministic workload in one process and writes one JSON
line. Run it on Linux with `/proc/self/smaps_rollup` available:

```sh
./build/benchmark mixed 12345 100000 system

LD_PRELOAD="$PWD/build/liballocator.so" ALLOC_STRATEGY=best \
    ./build/benchmark mixed 12345 100000 best

LD_PRELOAD="$PWD/build/liballocator_with_stats.so" ALLOC_STRATEGY=best \
    ./build/benchmark mixed 12345 100000 best
```

The arguments are `WORKLOAD SEED STEPS [EXPECTED_ALLOCATOR] [--size-scale N]`. The seed must be a
nonzero 32-bit decimal integer; the step count must be positive. The optional
expected label is `system`, `first`, `best`, or `next`. The executable identifies
the actual library supplying all four allocation functions using
[`dlsym`](https://man7.org/linux/man-pages/man3/dlsym.3.html) and
[`dladdr`](https://man7.org/linux/man-pages/man3/dladdr.3.html); an unexpected
provider or strategy causes failure. Custom libraries
must use the filenames generated by the Makefile. `--help` prints usage.

| Workload     | Requests                                                                               |
| ------------ | -------------------------------------------------------------------------------------- |
| `uniform`    | Allocate/free 64-byte objects.                                                         |
| `mixed`      | Mostly 1–2,048 bytes, with occasional 4–36 KiB requests.                               |
| `fragmented` | Keep alternating initial blocks live and churn 1–3 KiB allocations in the other slots. |
| `resize`     | Grow/shrink objects through `realloc`, up to 16 KiB, with occasional frees.            |

All workloads use 1,024 fixed slots. Every requested byte is written, and samples
at the beginning, middle, and end check payload contents and resize preservation.
The seed determines requests independently of allocation addresses. Timed API
counts, live requested bytes, peak live requested bytes, and checksums should
agree across allocator variants for the same workload, seed, step count, and size scale.

`CLOCK_MONOTONIC` measures the workload, including random-number generation,
payload checks, and writes. Fragmented-workload setup contributes 1,536 API calls
in addition to the requested steps. Heap validation, memory/stat snapshots,
final verification, final cleanup, and JSON printing are outside the timer.
Cleanup calls are reported separately. Increase steps for stable timings;
short example runs are not a full performance evaluation.

JSON includes the provider library, allocator variant (`glibc`, `plain`, or
`stats`), elapsed nanoseconds, calls per second, per-API counts, workload payload
totals, and three checkpoints: `initial`, `before_cleanup`, and `after_cleanup`.
Each checkpoint contains RSS in KiB from `smaps_rollup`, an approximate
process-lifetime RSS peak from `VmHWM`, and the complete allocator stats or `null`
when unavailable. RSS includes the whole process; requested-byte totals describe
only workload allocations. Allocator stats also include runtime allocations.
Use the plain library for primary timings and the stats library for diagnostic
replays. Memory values are captured before result printing allocates any buffers.

`make check-benchmark` runs short regression cases for all workloads and allocator
variants, checks matching traces and accounting, and exercises invalid input and
preload detection. It does not generate a performance report or saved dataset.

### Collect benchmark results

Build with `make`, then run:

```sh
python3 benchmark.py --mode both --seed 12345 --steps 100000
```

On macOS, use the existing Linux Docker image after building the binaries:

```sh
docker run --rm --network none -v "$PWD:/work" spp-allocator \
    python3 benchmark.py --mode both --seed 12345 --steps 100000
```

The runner covers all four workloads with glibc and both custom libraries. Each
custom library runs with `first`, `best`, and `next`: 28 configurations in total.
`--mode single` executes each configuration once; `--mode average` executes it
10 times in fresh processes with identical parameters. The default, `both`,
collects an independent single run plus 10 runs per configuration (308 processes).

`--mode average-seeds` averages 10 runs with different seeds. The first uses
`--seed`; each subsequent seed is derived from the previous one using xorshift32
(shifts 13, 17, and 5, with 32-bit unsigned arithmetic). Every configuration uses
the same sequence of 10 nonzero seeds, so the entire collection is repeatable.
Use `--mode all` to collect all three modes (588 processes).

```sh
python3 benchmark.py --mode average-seeds --seed 12345 --steps 100000
```

Results go to `benchmark_results/benchmarks.json`; use `--output PATH` to change the location.
The JSON has `single` and/or `average` lists. Each entry contains `repetitions`
and a `result` with the C benchmark's fields. Average results contain arithmetic
means for elapsed time, throughput, and all numeric checkpoint measurements.
Throughput is the mean of the reported rates. Unavailable measurements stay
`null`; identifiers, deterministic workload counts, and checksums stay exact.
Individual repetitions are not saved in average mode.

For `average-seeds`, JSON contains an `average-seeds` list. Each entry records
the exact `seeds` and corresponding `checksums` lists alongside `repetitions`
and `result`. The result averages timing, checkpoints, operation counts, live
and peak requested bytes, and cleanup counts. It omits the singular `seed` and
`checksum` fields, since neither has a meaningful average. All other identifying
fields remain unchanged. Per-run measurements are not saved.

Use `--size-scale N` with either `benchmark.py` or `build/benchmark` to multiply
every allocation size by a positive integer. The default is `1`, preserving the
original sizes. For example:

```sh
python3 benchmark.py --size-scale 16 --output build/benchmarks-scale16.json
./build/benchmark mixed 12345 100000 system --size-scale 16
```

This preserves allocation/free decisions and relative size distributions, and
also scales the initial fragmented-workload allocations. JSON records
`size_scale`; checksum comparisons apply to identical scales. The C benchmark
rejects scales that could overflow request sizes or total live-byte accounting
before starting the workload. Larger scales increase memory usage and payload
writing time; the slot count remains 1,024.

Checksums must match across repetitions and allocator configurations with the
same workload, seed, step count, and size scale. Different seeds are allowed to
produce different checksums. A mismatch or failed process stops the script with a nonzero exit
status. The output file is written only after all runs succeed; a previous file
is left untouched if collection fails. No charts or report are generated.

## Data structures

- **Arena list:** a doubly linked list of all currently mapped arenas, including
  the spare. Each arena records its neighbors and total mapping length.
- **Physical block chains:** each arena has its own doubly linked chain of blocks
  in memory order. These links identify adjacent blocks for merging.
- **Free list:** one global doubly linked list contains free blocks from all
  arenas. Blocks are inserted at its head, so its order can differ from physical
  order.
- **Next Fit cursor:** identifies where the next search starts. Removing a free
  block repairs the cursor if necessary; splitting sets it to the remainder.

`ALLOC_STRATEGY` selects `best` or `next`; other values, including an unset
variable, select First Fit. First Fit takes the first suitable free-list entry,
Best Fit takes the smallest suitable entry, and Next Fit searches from its cursor,
wrapping around once.

## Metadata layout

Each mapping starts with an arena header, followed by block headers and payloads:

```text
[arena header][block header][payload][block header][payload] ...
```

An arena header stores `prev`, `next`, and `length`. Each block header stores:

| Field                    | Meaning                                                                       |
| ------------------------ | ----------------------------------------------------------------------------- |
| `capacity`               | Payload bytes physically available in this block; excludes its header.        |
| `requested`              | Bytes requested by the caller; may be smaller than capacity. Due to alignment |
| `prev`, `next`           | Physical neighbors within the same arena.                                     |
| `free_prev`, `free_next` | Neighbors in the global free list.                                            |
| `arena`                  | Pointer to the owning arena.                                                  |
| `free`                   | Whether the block is available for allocation.                                |

The headers are unions containing both their metadata struct and a `max_align_t`
member. That member ensures suitable header alignment; it is not used to store
data. Header sizes and payload capacities are multiples of
`A = _Alignof(max_align_t)`, keeping subsequent headers and payloads aligned.

For a block pointer `b`, `b + 1` points to the payload's beginning. From the exact
payload pointer returned to the caller, `(block *)ptr - 1` recovers the header.

## Splitting and merging

Allocation reserves at least one byte and rounds the storage requirement up to
a multiple of `A`. A block is split only when the leftover space can hold another
block header plus at least `A` payload bytes. Otherwise, the allocation keeps the
whole block. Any free right neighbor is merged into the remainder before the
remainder is added to the free list. Shrinking an allocation uses the same
splitting logic.

Freeing immediately merges any free physical neighbors on either side. Merging
preserves the left header and absorbs the right header and payload into the left
block's capacity. It updates links without moving payload bytes. Participating
free-list entries are removed before merging, and the resulting free block is
inserted once. Blocks from different arenas are never merged.

## Mapping and unmapping

When no free block fits, `mmap` creates a readable, writable, private anonymous
mapping. The normal arena size is 64 KiB rounded up to whole system pages. Larger
requests receive a larger mapping that includes both headers and the payload,
also rounded to whole pages. The page size comes from `sysconf(_SC_PAGESIZE)`,
with a 4096-byte fallback. Size arithmetic is checked before mapping.

After freeing and merging, a single free block with no physical neighbors means
the entire arena is empty. The allocator retains one normal-sized empty arena
as `spare`; other empty arenas are passed to `munmap`. The spare stays in the
arena list with its block in the free list. Allocating from it clears the spare
marker.

Before unmapping, the allocator saves the arena's length and list neighbors and
removes its free block. Success unlinks the arena using the saved pointers.
Failure restores its free-list entry, so the mapping remains reusable; this can
leave additional empty arenas mapped.

## Concurrency

One global mutex protects initialization, arena and free lists, block metadata,
and the spare and cursor pointers. Public allocation functions acquire it;
internal helpers run while it is held.

## Statistics and diagnostics

Build `allocat_with_stats.c` instead of `allocator.c` to enable statistics and
diagnostics. The two files are independent versions exporting the same allocation
functions; compile only one into a given allocator library.

Include `allocator_stats.h` to use the instrumented version's diagnostics:

- `allocator_get_stats(&stats)` copies a consistent snapshot into a
  `struct allocator_stats`. It returns `0` on success or `-1` for a null pointer.
- `allocator_validate()` returns `1` when arena/block links, alignment, free-list
  state, and live-memory accounting are consistent, or `0` otherwise.
- `allocator_strategy_name()` returns `"first"`, `"best"`, or `"next"`.

Snapshots report current and peak mapped bytes, arena and live-block counts,
requested bytes, allocated payload capacity, and free-space distribution.
`capacity_bytes - requested_bytes` measures slack inside live allocations;
headers are excluded from both values.

Call counters are cumulative and include failures and `free(NULL)`. Internal
allocation and release during `realloc` do not increment `malloc_calls` or
`free_calls`. Search, split, merge, and mapping-attempt counters are also
cumulative. Mapped-byte and arena totals change only after successful system
calls. Free-block statistics are calculated from the free list for each snapshot.
`average_free_block_size` is the mean free payload capacity in bytes, including
the spare's free block and excluding headers. It is a `double` to preserve
fractional averages, or `0.0` when no free blocks exist. It is calculated in
`allocator_get_stats` from the same snapshot's free bytes and block count, so
validation does not need to run first. Rebuild consumers with the updated
`allocator_stats.h` when using the extended statistics structure.
All diagnostics use the existing mutex and perform no allocations.
